# OpenBSD最新版での動作確認計画

作成日: 2026-11-09（日本時間）。以下は作業開始時の検証計画。

実施状況: 同日に[検証を完了](openbsd-verification_ja.md)した。4 vCPUでの起動遅延を受け、機能・性能の確認は1 vCPU・16 GiBで行った。以下は作業開始時の計画を基本に、実際のOpenBSD用検査コマンドを反映している。

## 対象と目的

[OpenBSD公式サイト](https://www.openbsd.org/)で作成日時点の最新正式版 **OpenBSD 8.0（2026-10-20公開）** を確認した。初回対象はamd64とし、実行開始時に最新正式版を再確認する。更新されていれば対象版・メディア・パッケージ配布先を合わせて更新する。スナップショット版は初回対象に含めない。

Folimeldをソースから実行し、依存導入、既存テスト、実GUIでの編集・保存、保存済みPDFの内容、再起動後の再現性を確認する。単体実行ファイルの作成、OpenBSD向け配布、他アーキテクチャの対応判断は別作業とする。

## 1. 専用VMとOSを準備する

1. ホストの空きメモリ・ディスク、VirtualBoxの版、既存VMとポートの使用状況を確認する。
2. `Folimeld-OpenBSD-8.0-amd64` を新設する。初期案は4 vCPU、8 GiB RAM、80 GiBの専用可変ディスク、3D無効、NAT。ソースビルドで不足する場合は正常停止後に資源を増やし、変更前後を記録する。
3. SSH転送は `127.0.0.1:2225` → ゲスト22番を候補とし、空き確認後に確定する。既存FreeBSD・NetBSD VMのディスクや転送設定は変更しない。
4. [公式ダウンロード案内](https://www.openbsd.org/faq/faq4.html#Download)から対象版のamd64用インストールメディアを取得し、公式の署名付きチェックサムを信頼できるリリース公開鍵で検証する。URL・署名検証結果・実ファイルのSHA-256を保存する。
5. インストール先が専用の空ディスクであることを容量とデバイス名で確認する。基本セット、コンパイラー、X関連セットを導入し、一般ユーザー `folimeld`、鍵認証SSH、日本時間を設定する。秘密鍵・認証情報はGitへ保存しない。
6. ディスク起動とSSHを確認し、対象版に適用可能な公式更新を適用する。`uname -a`、`sysctl hw`、更新履歴、パッケージ一覧を記録する。
7. 一般ユーザーでX11デスクトップを起動し、日本語フォント、UTF-8のファイル名、マウス・キー入力、画面解像度を確認する。Guest Additionsや共有フォルダーの利用可否は未確認とし、転送はSSH/SCPを基本にする。
8. OS導入済みの復旧用スナップショットを保存する。

到達条件: 再起動後も一般ユーザーのGUIと鍵認証SSHが使えること。

## 2. 依存関係の成立を先に判定する

[公式パッケージ管理FAQ](https://www.openbsd.org/faq/faq15.html)に従い、対象リリースのパッケージを優先する。`pkg_info -aQ` でPython、PySide6/Shiboken6、Qt 6、PyMuPDF/MuPDF、Pillow、cryptography、pytest、psutil、mypy、Ruff、PyInstallerを調べる。名称・提供版・提供アーキテクチャは現時点で未確定。

- `requirements.txt` と実際の提供版を比較する。特にPySide6 >= 6.7、Pillow >= 11、cryptography >= 46かつ < 51を確認する。
- PyMuPDFのOpenBSD向け現行下限は1.24だが、FreeBSDでのフォーム不具合を踏まえ、初回候補は1.28.2以降とする。修正済みであることは先行テストで判定する。
- `constraints-release.txt` はWindowsで検証した固定版を含むため、そのまま導入できると仮定しない。相違する版、導入元、依存制約との整合性を一覧にする。
- PySide6とPyQt6は置換しない。PyMuPDFとMuPDFのコマンドラインツールも区別する。
- 専用の `.venv-openbsd` を作る。OSパッケージを参照する必要がある場合は `--system-site-packages` を使用し、実際にimportしたファイルの場所と版を記録する。
- 不足する依存はソースビルドへ切り替える。Qt/PySide6/Shiboken6の組み合わせ、Clang/libclang、CMake、Ninja、SWIG等の必要条件を各ソースの定義で確認する。PyMuPDFの同梱MuPDF、暗号化依存のRust/CFFI等も調査する。
- NetBSD/FreeBSD用wheelやビルドスクリプトを無変更で流用しない。OpenBSDの公式portsに該当パッチがあれば内容を確認し、適用したソースのハッシュ・差分・コマンド・ログを残す。
- PyInstallerは既存のソース同梱テストでも参照されるため調査対象に含める。importできてもOpenBSD向け配布物を作成できるとは判定しない。

到達条件: PySide6のCore/Gui/Widgets、PyMuPDF、Pillow、cryptographyを一般ユーザーでimportでき、Qtの最小ウィンドウ表示とPDFの生成・再読込が成功すること。依存が成立しなければ失敗ログと最小再現をまとめ、この段階で検証未完了とする。

## 3. フォーム回帰と既存テストを実行する

検証対象のコミットSHAと未コミット差分を固定してゲストへ転送する。以下はリポジトリールートで実行する予定のコマンド。

```sh
mkdir -p build/openbsd-verification
.venv-openbsd/bin/python -m pip check
QT_QPA_PLATFORM=offscreen .venv-openbsd/bin/python -m pytest -q -p no:cacheprovider tests/test_pdf_forms.py tests/test_save_contents.py
QT_QPA_PLATFORM=offscreen .venv-openbsd/bin/python -m pytest -q -p no:cacheprovider --junitxml=build/openbsd-verification/pytest.xml
ruff check --exclude .venv-openbsd .
.venv-openbsd/bin/python -m mypy
```

各コマンドの標準出力・標準エラーと終了コードを保存する。offscreenプラグインを使用できない場合は実X11上で実行し、その条件を記録する。

フォーム回帰を先行し、異常終了時にはQt/Folimeldを除いたPyMuPDF単独コードで切り分ける。依存パッチが必要なら、その最小再現と回帰テストを再実行してから全件へ進む。

既存テストの成功・失敗・スキップ数と理由を記録する。機能を無効化したり失敗ケースを除外したりして全件合格と扱わない。工具がOpenBSDで実行できない場合は未実施理由を残し、ホスト実行の結果をOpenBSDネイティブの結果と区別する。`pip check` に加え、pipメタデータに載らない手動ビルド依存も確認する。

## 4. 実GUIと保存結果を照合する

原本を複製し、一般ユーザーの実X11セッションでメニュー、ツールバー、ダイアログ、キー操作を使う。アプリ内部APIによる操作は実GUIの確認に含めない。

| 分類 | 操作と合格条件 |
| --- | --- |
| 起動・表示 | `testdata/tameshibu_episode3_ja.pdf` の8ページと日本語が表示され、スクロール・複数選択ができる |
| 編集 | ページ移動、左右回転、削除、白紙・別PDF挿入、Undo/Redoが期待どおりに働く |
| 保存 | 別名保存と検証用コピーへの上書きが完了し、再読込でもページ数・順序・回転・内容が一致する |
| パス | 日本語・空白を含むディレクトリーとファイル名で開く・保存ができる |
| フォーム | テキスト・チェック・選択肢のないウィジェットを含むPDFを開き、編集・保存・再読込して値・属性を維持する |
| パスワード | 正誤の入力・キャンセル、設定・変更・解除を確認し、保存結果の暗号化状態を照合する |
| 文書設定 | PDFバージョン、レイアウト、綴じ方向を変更し、保存後に照合する |
| 画像取り込み | 対応形式、自然順、除外、複数ページTIFF、向き・透明部分・サイズを確認する。キャンセル・不正画像で元の文書を維持する |
| エラー復旧 | 書込不可ディレクトリー等への保存でエラーを表示し、文書と既存ファイルを保持する。その後別の場所へ保存できる |
| 一時データ・履歴 | 大きな編集で履歴退避と復元が働き、通常終了時に不要な一時ファイルが解放される |
| 設定・終了 | 表示言語とサムネイルサイズが再起動後も保持され、未保存の変更を伴う終了で確認画面が出る |

保存結果はGUI表示に加えて、ページ数・順序・回転・内容ストリームのハッシュ、フォーム値・属性、文書設定、暗号化状態を読み取り専用スクリプトで照合しJSONへ保存する。可能な範囲で別のPDFビューアーでも描画を確認する。画像変換は画素・ページ寸法等を使って確認する。

## 5. 負荷試験と再起動を確認する

既存の `tools.benchmark_pdf` で100ページ、画像入り100ページ、1000ページを各3回以上、新規プロセスで測定する。コマンドは[開発ガイド](../DEVELOPMENT_ja.md)に合わせ、出力先を `build/openbsd-verification/` にする。

- 操作時間、スクロール描画、最大保持サムネイル数、RSS、中央値とばらつきを記録する。
- 実GUIでも1000ページ目の表示、編集、保存、再読込を行う。長時間処理中の進捗表示と操作復帰を確認する。
- 既存BSDの測定値は参考にし、VM資源や依存版が異なる値をそのまま性能合否の閾値にしない。完走・出力一致・異常終了の有無を必須判定とする。
- 正常終了後にVMを再起動し、鍵認証SSH、一般ユーザーのGUI、確定した仮想環境からの起動、保存済みPDFの再読込を再確認する。
- 全工程後、正常停止して検証済みスナップショットを保存する。

## 証跡と最終判定

作業中のログ・生成PDF・ビルド資材は `build/` 配下へ置く。レビュー用証跡は `documentation/openbsd-verification/`、最終記録は `documentation/openbsd-verification_ja.md` へまとめる。秘密鍵、実データ、実用パスワード、大容量ビルド生成物は含めない。

記録には、OSと更新状態、VM構成、ソースSHAと差分、依存の版・import先・導入元、ビルドパッチ、終了コード、JUnit XML、GUI画像、保存結果JSON、性能JSON、未確認項目と再現手順を含める。

完了条件は、依存成立、理由を確認したスキップを除く全件テスト成功、必須GUI項目成功、保存内容の一致、負荷試験完走、再起動後の再現である。失敗・未実施は項目ごとに明記し、「起動のみ」「部分確認」「本計画の範囲で確認済み」を区別する。結果は検証したOS・アーキテクチャ・依存構成に限定する。

現段階ではREADMEの対応OS表を変更しない。検証結果に基づいて対応範囲を追記する場合は、`README_ja.md` と `README.md` を同時に更新する。
